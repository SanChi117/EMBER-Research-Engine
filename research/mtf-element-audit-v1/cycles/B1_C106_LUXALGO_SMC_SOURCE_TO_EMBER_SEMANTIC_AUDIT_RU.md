## Критические и существенные риски, подтверждённые именно исходником

1. **КРИТИЧЕСКИЙ FVG future/HTF repaint risk:** строка 635 в `request.security(..., lookahead = barmerge.lookahead_on)` одновременно запрашивает **high[0], low[0], time[0]** более крупного TF. TradingView официально допускает non-repaint higher-TF technique только с appropriately offset [1] data либо полностью подтверждёнными свечами; неперемещённые current high/low при lookahead_on могут давать historical future data и realtime незавершённость. `timeframe.change` в 638 не доказывает, что текущая HTF свеча закрыта. **Запрет брать FVG labels как точные timestamps доступного реального сигнала**, особенно при запуске индикатора на 15m для FVG 4H. При одинаковом chart TF сценарий другой, поэтому без платформенного Pine теста не утверждать, что _каждый_ label future.
2. **КРИТИЧЕСКИЙ backdated pivot timestamps:** 337–345 и 409–457 используют `high[size]`/ `low[size]`, время `time[size]`, индекс `bar_index[size]`: визуально pivot рисуется в прошлом; фактически подтвердился только на текущем баре. На 4H TF default swing 50 bars = **200 часов ≈8.3 дней** задержки; internal 5 bars = 20 часов. **Нельзя импортировать timestamp метки как timestamp появления у алгоритма**. C105 4H pivot 2 right bars = 8h delay by different definition.
3. **СУЩЕСТВЕННЫЙ realtime intrabar signal risk:** строка 568/593 реагирует на `ta.crossover(close,...)`/`ta.crossunder`, но код не содержит `barstate.isconfirmed` как обязательного gate для signal/alert. TradingView alerts на незакрытом баре в зависимости от настройки способны менять состояние; нужен только completed bar and alert Once Per Bar Close плюс самостоятельный event lock. `varip` 293–295 находится в контроле chart bar, но как бы ни использовался, не заменяет chronological close proof.
4. **СУЩЕСТВЕННЫЙ confluence expression:** строки 556–557 сравнивают верхний wick с `math.min(close, open - low)`, то есть практически с величиной `open - low`, а НЕ с обычной длиной нижней тени `min(open,close)-low`. Числовой контрпример O=100 H=103 L=98 C=99: upper wick 3, lower wick 1, исходное выражение `3 > min(99,2)` истинно; отличается при O=100 H=102 L=98 C=99: upper wick 2 vs lower wick 1, но RHS 2 => false. Это подозрительная формула / возможная ошибка предоставленного варианта, а не проверенная errata от LuxAlgo. В C105 такого фильтра нет.
5. **СУЩЕСТВЕННОЕ:** OB `highVolatilityBar` 319–323 переставляет parsed high/low на extreme свечах; `storeOrdeBlock` 507–523 ищет extrema этих transformed values. Это специфический эвристический ценовой диапазон; не использовать для 4H SL без валидации bounds.
6. **СУЩЕСТВЕННЫЙ distinction:** код выводит strong/weak исключительно по `swingTrend.bias` (728/733). Это **не Strong High/Low в академическом смысле доказанного swing-инвалидатора** и не механически валидная 4H SL boundary.
7. **СУЩЕСТВЕННЫЙ difference FVG lifecycle:** исходник удаляет FVG после полного price traverse дальней границы (625–630); C105 инвалидирует 4H parent по **4H close** за краем и истечению 48h; правила невзаимозаменяемы. Вход C105 использует первое касание; LuxAlgo отображает длительно живущие зоны. Нужно предварительно выбрать и зафиксировать semantics до тестирования.
8. **ПРАВА И ИСТОЧНИК:** нельзя без выполнения условий CC BY-NC-SA заливать/коммерциализировать чужой Pine в другом движке. Лучшее решение — **независимый собственный алгоритм по концептам** с указанием референса и отдельно проверенной временной семантикой, без копирования защищённой реализации.

## Что реально полезно для нашей 4H MTF архитектуры
- **Приоритет P0:** независимые 4H/internal структуральные BOS/CHoCH и 4H swing extents, с реальными `confirmed_at` и `available_at` timestamp, без backdating; предварительно проверять на оригинальных OHLC, не по нарисованной метке.
- **P1:** 4H FVG с учётом силы middle candle / displacement, explicit untouched/partially-filled/invalidated lifecycle. Актуальная C105 функция FVG по одной геометрии gap, **без strength threshold**, это потенциально объясняет 15/25 SL. Гипотеза, НЕ доказательство.
- **P1:** 4H OB и EQH/EQL как новые **дополнительные источники parent POI/выхода**, отдельно и последовательно; только после isolated semantic validation. Не переносить образы из LuxAlgo автоматически.
- **P2:** premium/discount, old D/W levels как context features. Сами по себе не предполагают edge.

## Рекомендуемый безопасный эксперимент C106-B (ещё НЕ запущен и НЕ изменяет C105)
1. Сначала создать независимый **structure-event oracle**: для каждого события 4H/1H/15m получить `pivot_price`, `pivot_bar_closed_ms`, `confirmed_at_ms`, `available_at_ms`, `crossed_at_ms`, `parent_zone_id`, `source_semantics`, `invalidated_at_ms`.
2. До новых рыночных данных зафиксировать: если 4H external swing отсутствует — не подменять internal swing; 15m lower signal подтверждается только после 1H и 4H родителя; P4 SL и TP по-прежнему только от 4H.
3. Синтетические adversarial тесты: latent swing confirmation, gap built from 3 fully closed 4H, future leaking `security`, touch/mitigation vs invalidation, BOS vs CHoCH with previous bias, 4H stop/target source; first ensure baseline C105 byte/SHA unchanged.
4. Только после semantic agreement оценить реальный экономический эффект в **новом frozen OOS**, не на ранее просмотренных 25 trades C105 как на untouched data. Не улучшать пороги на основе результатов.

## Итог текущего этапа
**Аудит завершён, но перенос в торговый механизм НЕ утверждён.** LuxAlgo — качественный набор визуальных **референсных концептов**, а не сертификат корректности source time и не готовая стратегия. По безопасности входов больше всего пригодны BOS/CHoCH distinction и структура swing; главная проблема — задержка и unconfirmed FVG HTF. **C105, SL, TP, RR, PnL, source frozen SHA и PAPER пороги не менялись**. Архитектура построения 4H SL/TP остаётся владельцем стратегического риска, младшие TF — только точка входа.

Прямое указание: «если в этом скрипте не те части которые нам нужны не нужно их добавлять». **Итог C106 текущей фазы: audit only; NO NEW LUXALGO DETECTORS.** Для защиты объёма/сложности два временных C106 прототипа общего BOS/CHoCH/FVG event API и его тестов были удалены из исследовательского каталога до принятия решения об интеграции. Не добавлять unrelated premium/discount, OB, EQH/EQL, internal/swing state machine и алерты «просто потому, что они есть в LuxAlgo». На следующем этапе сначала по одному проверять явную потребность уже имеющегося C105 элемента: (а) точная причинная регистрация существующего 4H FVG, (б) время подтверждения 4H pivot для TP, (в) корректность текущих 1H reaction и 15m VC. Только при воспроизводимо доказанной ошибке и согласовании с целевой MTF-последовательностью вносить минимальное изменение с adversarial тестами и новым неподсмотренным PAPER OOS.
