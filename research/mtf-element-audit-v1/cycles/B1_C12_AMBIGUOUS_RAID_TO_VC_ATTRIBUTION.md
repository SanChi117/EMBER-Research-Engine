# B1/C12 — двухсторонняя проверка причинной неоднозначности 1H Raid → 5m IMB

**Дата:** 2026-10-16. **Область приёмки:** независимая **source-bounded диагностика двудольного графа кандидатов**, а не академически утверждённая механика назначения конкретной VC/StrongHL. **PAPER ONLY, 0 orders, 0 ready.**

## Источник → инженерный вопрос

Оригиналы Google Drive:
- [Strong High & Low](https://drive.google.com/file/d/1lvPRbhfM6ZjfW7UP-30y9uND1R6VC13t/view): StrongHL требует контакт с ликвидностью/неэффективностью и последующее подтверждение движения через VC POI или BOS. Контакт и IMB сами по себе не исчерпывают авторское подтверждение.
- [Imbalance](https://drive.google.com/file/d/1ajvG1554qQ-5AnIV8HVmoDflkNRrU-LN/view): три закрытые свечи с wick gap; первый контакт зоны после её образования имеет значение, произвольные 50% не обязательны.
- [Entry by IMB & SNR](https://drive.google.com/file/d/1hkKKwy60-VIoqEsVYAq12mnPZA7ySXFQ/view): нужен старший контекст и выбранная соответствующая ветка TF; 1H liquidity/POI поддерживает решение только в рамках MTF.

**Найденное ограничение:** ни один из использованных первоисточников не утверждает универсального технического правила «назначить ближайший IMB к каждому Raid», «первый IMB всегда VC этого Raid», «время ожидания N минут», «максимум один VC на Raid». Добавлять эти фильтры сейчас значило бы создавать неавторскую стратегию. Один и тот же IMB может идти после нескольких Raid, один Raid — до нескольких IMB.

## Код

- `d05/c12_attribution_ambiguity_gate.py`: чистая read-only проверка всех ценовых `ContactImbPriceWitness` C11, группировка двудольных связей **по Raid ID и отдельно по IMB ID**. Выдаёт самостоятельные `AttributionNode`: `MULTIPLE_GEOMETRIC_IMBS_NO_AUTHOR_CHOICE`, `MULTIPLE_PARENT_RAIDS_NO_AUTHOR_CHOICE`, `SINGLE_GEOMETRIC_MATCH_STILL_UNCERTIFIED`. **Один-к-одному геометрический узел тоже не получает академический signoff.**
- Отвергаются дублированные рёбра, разные цены/сырой источник для одного IMB, неверный символ, фиктивные таймштампы, неправильный source start/end, будущий IMB, приписанный прошлому «первый тест», попытка пометить StrongHL или READY как утверждённые. Все решения `NOT_TRADE_READY`.
- `d05/test_c12_attribution_ambiguity_gate.py`: **25** adversarial-positive/negative тестов, включая специально созданные связи один→много и много→один, одинаковый IMB с изменённой геометрией, префикс и double counting. Не изменён изначальный C11/F06/v05.
- `tests/probe_c12_real_attribution_graph.py`: независимое повторное получение **10 оригинальных Binance USD-M Futures 5m ZIP + same-host .CHECKSUM**, сверка SHA ZIP+CSV с SHA-замороженным F06; параллельно проверяется неизменность сохранённого результата C11 и ещё одной квитанции C12 по всей таблице инструментов.
